> 本文是 `design/prompt_init.md` 的配套设计文档，固化了五个优化方案讨论后确定的组件边界与三个贯穿全局的抽象。

## 一、分层架构与职责红线

```
┌─────────────────────────────────────────────────────────────┐
│  QQ 客户端                                                   │
└───────────────┬─────────────────────────────────────────────┘
                │ QQ 协议
┌───────────────▼─────────────────────────────────────────────┐
│  NapCat                                                      │
│  职责：提供 QQ 协议接入，收发消息/文件                        │
└───────────────┬─────────────────────────────────────────────┘
                │ 事件
┌───────────────▼─────────────────────────────────────────────┐
│  LangBot (Python)                                            │
│  职责：消息路由、插件管理、前置拦截、拟人延迟、文件 I/O       │
│        主动发送（暴露 send_message 供后端调用）               │
└──────┬──────────────────────────────────────┬───────────────┘
       │ 复杂意图                              │ 事实记忆写入/读取
┌──────▼──────────────┐              ┌────────▼───────────────┐
│  Dify               │              │  Spring Boot            │
│  职责：意图识别、    │   Tool 调用  │  职责：状态机、持久化、  │
│  Agent 编排、对话流、│◄────────────►│  定时调度、画像存储、    │
│  决策「填什么/发不发」│              │  草稿中心、防重状态      │
└─────────────────────┘              └────────┬───────────────┘
                                              │ REST / WebSocket
                                     ┌────────▼───────────────┐
                                     │  Vue3 前端              │
                                     │  草稿中心、备忘录、      │
                                     │  记忆总控台、设置        │
                                     └────────────────────────┘
```

### 职责红线（不可逾越）

| 红线 | 说明 |
|---|---|
| **业务逻辑不写进 Dify Prompt** | Dify 只做语义理解、意图识别、对话流、决策**以及「调哪个写接口、填什么参数」**；状态机 / 持久化 / 定时调度归 Spring Boot，文件 IO 归 LangBot 插件（见方案 ④）|
| **Dify 不得自己实现业务规则** | 通过 `POST /api/agent/ops` 发起**窄写操作**（`memo.create/update/close`），校验、归属、状态迁移、提醒重算、审计、幂等一律由 Spring 执行。提示词里不许出现提醒策略、状态迁移规则、阈值。不视为「Dify 直接写业务表」 |
| **Dify 严禁直接处理文件流** | 文件二进制读写由 LangBot 插件（Python）承担；Dify 只做「决定填什么」 |
| **风格记忆禁止实时改 System Prompt** | 只允许定期离线总结后更新画像 Prompt；事实记忆才可实时写 |
| **Spring Boot 不直连 NapCat** | 一切 QQ 侧动作（发消息/发文件）经 LangBot 封装，协议细节不泄漏进业务层 |
| **检索规则不进 Dify** | 七路召回、RRF 融合、时间软分段、预算截断、终态表与 `scope` 全在 Spring；Dify 只做 resolve / answer / expand 的语义判断。检索只服务前端 `/api/ask`，不接入 QQ 端 |

> 第二、三条是本项目历史上最容易被误读的地方：Dify **可以**发 HTTP 去改数据（否则“改哪条备忘”
> 永远表达不出来，见 `agent_contract.md` §3），但**不可以**自己判断“能不能改、改成什么状态”。
> 判据只有一条：**规则（阈值/枚举/状态机/重算）出现在哪里**。出现在 Dify 的提示词或代码节点里 = 越线；
> 出现在 Spring 的服务层 = 合规。

### 检索职责（F4+ 智能检索）

`/api/ask` 的检索链路（详见 [`intelligent_retrieval.md`](./intelligent_retrieval.md) §7）：

| 环节 | 归属 | 说明 |
|---|---|---|
| 语义理解 | **Dify** | `stage=resolve` 抽实体/关键词/改写查询/时间区间；`stage=answer` 在候选集内作答并给 `used_ids`；`stage=expand` 在证据不足时给新检索串/实体。Dify **不接触消息表** |
| 七路召回 | **Spring** | `note / msg-person / msg-mention / msg-lexical / msg-semantic / memo / file`；除 `msg-person` 按主体外，其余不带会话过滤 |
| 融合与截断 | **Spring** | RRF（`Σ 1/(60+rank)`）去重、时间软分段、30000 字符 / 150 条预算 |
| 终态与 scope | **Spring** | 证据校验、反问/降级/找不到的终态表、`scope` 的通道计数与 `message` |
| 文件 I/O | **LangBot 插件** | 不变；检索不读写文件正文，也不改动插件 |

**检索只由前端「查询」页调用 `/api/ask`**：QQ 端不提问、插件不改；Spring 也不为了检索去调 NapCat。
模型推理跑在 Spring 进程内（ONNX）或走外部 OpenAI 兼容端点，不引入 Dify Dataset 双写。

### 各组件擅长的能力

| 组件 | 擅长 | 不擅长（别放这里）|
|---|---|---|
| **Dify** | 语义理解、意图识别、对话流、灵活决策 | 状态机、文件 IO、持久化、定时任务 |
| **Spring Boot** | 状态机、文件元数据/业务持久化、定时调度、REST API | 直连 QQ、处理文件二进制流、改 Dify 配置以外的业务 |
| **LangBot** | QQ 交互、消息/文件收发、正则拦截、Python 文件库、拟人化 | 复杂业务状态、长期持久化 |
| **Vue** | 展示、人工确认、手动编辑、配置 | 业务逻辑判定 |

## 二、三个贯穿全局的抽象

五案在讨论中反复出现同类需求（草稿确认出现 4 次、消息日志被多案复用、主动发送被 2 案复用）。为避免重复代码，统一为以下三个抽象，**Phase 1 建表时统一落地**。

### 抽象 1 · 统一草稿中心（`draft` 表）

**动机**：草稿/确认机制在「私聊回复」「文件回传」「备忘录创建」「事实记忆」四个方案中重复出现。各写一套会四倍重复。

**表（`draft`）关键字段**：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `type` | 草稿类型：`REPLY` \| `FILE` \| `MEMO` \| `FACT` |
| `sender_id` | 归属用户 |
| `payload` | JSON，各 type 自定结构（回复正文 / 文件引用 / 备忘字段 / 事实 kv）|
| `status` | `PENDING` \| `CONFIRMED` \| `REJECTED` |
| `created_at` | 创建时间 |

**超时行为**：**保持 `PENDING`**，不自动过期（用户主动处理，避免丢信息）。

**确认分发**：`POST /api/drafts/{id}/confirm` 由 Spring Boot 按 `type` 分发——
- `REPLY` / `FILE` → 通知 LangBot 执行发送
- `MEMO` / `FACT` → 直接写入对应业务表

**前端**：Vue 单一「草稿中心」页，按 `type` 分组筛选，一键确认/拒绝。

### 抽象 2 · 统一消息日志（`message_log` 表）

**动机**：风格记忆的总结原料 + 全链路排查依据。

**表（`message_log`）关键字段**：`id, sender_id, chat_id, direction(IN/OUT), content, msg_type, created_at`。

**写入方**：LangBot 在每个消息进出时调 `POST /api/message-logs`（异步、可批量）。

**消费方**：记忆分离方案的风格定期总结工作流。

### 抽象 3 · LangBot 主动发送接口（`POST /api/langbot/send_message`）

**动机**：Spring Boot 是「提醒发起者」「草稿确认执行者」，但发 QQ 必须经 LangBot。文本推送场景共用同一入口。

**契约**：`{target: {type: "private"|"group", id}, content, delay_ms?}`，由 LangBot 封装 NapCat 协议。

**调用方**：
- 备忘录提醒（方案 A：Spring Boot Quartz 到期扫描后调用）
- 草稿中心确认后（`REPLY` 类型的发送动作）

> 注：**发文件**（草稿 `FILE` 类型确认后、方案 ④ 回传）走 LangBot 的 `send_file` 接口，与 `send_message` 并列，不混用（文件是二进制，契约不同）。

## 三、五案 ↔ 组件职责总览

| 方案 | NapCat | LangBot | Dify | Spring Boot | Vue |
|---|---|---|---|---|---|
| ① 私聊拟人/草稿 | 协议 | 拟人延迟、按 `send_action` 路由、发送 | 输出 `send_action` + 内容 | 统一草稿中心 | 草稿中心页 |
| ② 统一回复防重拦截 | 协议 | 前置拦截（关键词+正则，热更新）、仍走防重 | 未命中时识别+生成 | `collection_task` 状态表、拦截规则配置 | — |
| ③ 备忘录分级提醒 | 协议 | `send_message` 主动发送、QQ 内闭环识别 | 识别邀约/通知 + 抽结构 + 打分 | `memo` 表、Quartz 调度、状态机 | 备忘列表、编辑、闭环 |
| ④ 文件业务后置 | 协议 | **文件下载/结构化读写/回传**、状态机、QQ 反问 | 决策「填什么」（`fills`+`missing`）| 事实画像读取 API | 状态展示 |
| ⑤ 记忆分离 | 协议 | 记录 `message_log` | 事实抽取 + 风格总结工作流 | 画像存储、定时调度、调 Dify 配置 API | **记忆总控台** |

## 四、跨方案的共性约定

1. **统一返回格式**：Spring Boot 所有 API 采用统一响应体（`{code, message, data}`），异常统一处理。
2. **异步优先**：耗时操作（文件处理、风格总结）一律异步，提交即返回 `taskId`，避免 Dify/LangBot 等待超时。
3. **幂等**：防重类接口（`collection-tasks/check`）幂等可重复调用；关键写入以业务 key 去重。
4. **置信度路由**：凡是「AI 判断可能出错」的产出（回复 / 文件 / 备忘 / 事实），一律可降级为草稿确认——这是全项目的一致性策略。
5. **人工兜底**：任何自动写入的记忆/备忘，用户都能在 Vue 侧手动增删改（记忆总控台 / 备忘列表）。

## 五、待 Phase 4 确认的集成点

- **Dify 应用配置 API**：方案 ⑤ 选「更新画像 Prompt」，需 Spring Boot 调用 Dify 的接口更新应用 system prompt。调用方式、鉴权、字段名需在 Phase 4 查阅最新官方文档确认。
- **LangBot 插件对外 HTTP 能力**：方案 ③④ 依赖 LangBot 暴露 REST 接口（`send_message` / `send_file`），需在 Phase 3 确认 LangBot 的插件对外接口机制。
- **NapCat 文件收发 API**：方案 ④ 文件下载/上传依赖 NapCat 的文件接口，Phase 3 确认。
